## The rules this redesign follows

1. **One primary action per screen**, and it has a key.
2. **Facts in one quiet line**, chips only for things that are non-zero or need you.
3. **Detail on demand**: collapsed by default, one click or one key away, remembered per browser.
4. **One setting, one meaning**: a thing that can be set is set in one place and drives every view.
5. **Status never by colour alone; keys never while typing or with a dialog open; Play Off stays the phase 2 page; theme tokens only, all 11 themes checked.**

## 1. The finish line: what counts as done

One setting, **Finish line** (Settings → Workflow), drives Play's quest, the Jobs list's Done group, the Done notification, the trail's flag, the Table's Done filter and the map:

| Choice | Done when | Why you'd pick it |
|---|---|---|
| PR #1 open | the Foreman opened PR #1 | today's quest rule |
| **PR #1 merged** (recommended default) | your work is on the Moxie branch | from here on it waits on other people (Raj, the release owner) |
| In staging | PR #2 merged | QA can see it |
| In main | the release PR carried it | the real end |
| When I mark it | you click Done | manual |

"When I mark it done" always counts, whatever the choice. Crossing the finish line is the celebration (confetti, the toast, "Quest done", the Done notification at the level you set). Reaching staging and main **after** the line are quiet "Landed" marks: a chip on the row, a silent notification if Done is on, no second confetti.

Implementation:
- `settings.workflow.finishLine` (server, `lib/state.js` defaults; `POST /api/settings {workflow}`), replacing `play.questDone` (migrate `first-pr` → `pr1-open`, `marked-done` → `marked`).
- One pure function `finishLineReached(job, lane, setting)` in `dashboard/lib/finish.js`, used by `play.js` (quest done), `snapshot.js` (`groupFor`), `server.js` `flowNotices` (Done vs Landed), and sent on each job as `finish: { reached, at, landed: 'staging'|'main'|null }` so the web never re-derives it.
- The trail (`play/extrasModel.ts`): the goal flag moves to the chosen stop; stops after it are drawn as "after the line" (smaller, no crew). The handoff's point stands: the crew member stands where the work is, even past the goal.
- Tests: table tests for `finishLineReached` across the five choices × lane positions; `play.test` for the migration; `flowNotices` Done vs Landed.

## 2. The PR stages: the brainstorm

The problem: after review, three PRs with three owners (you, Raj, the release owner), each with waits of days or weeks, drawn today as seven boxes per job that are mostly empty, and run as Foreman stages (`pr1`, `pr2`, `staging-qa`, `pr3`) that need go-aheads for things the Foreman mostly can't do (merge, approve).

Four directions, and the recommendation is all four together, since they fit:

**A. The ship track.** One horizontal track per job with five stops: worktree · fork · Moxie branch · staging · main. Filled dots up to where the work is, the finish-line flag on the stop you chose, one line of words under it ("On the Moxie branch · PR #2 open, waiting for Raj · 3 d"). The main ↑↓ and not-pushed counts become a muted suffix on that line, not chips. This replaces the 7-column lane. (Handoff direction 1.)

**B. The Shipping list.** A job past the finish line leaves the Foreman's daily loop. It moves out of Needs you / Running into a **Shipping** group (Jobs list, map, Table) that is purely observational: where it is, who it waits on, how long, and one link ("Open PR #2 on GitHub"). No gate cards, no Foreman turns, no stage chips. Done (main, or marked) is the group under it. This is what stops staging's long tail from looking like unfinished work.

**C. Nudges on the Desk, not stages.** The flow watch already sees PR #1 merge, PR #2 approve, and so on. Each hand-off becomes one Desk item with one key:
- PR #1 opened → "Self-review and merge PR #1 on GitHub" (link; `o` opens it). The dashboard never merges.
- PR #1 merged → "Open PR #2 to staging?" (`a` says yes; the Foreman prepares it, as the skill does today, with its own go-ahead logged).
- PR #2 open → "Ask Raj for a review?" (`a`).
- Raj approved → "Merge PR #2 on GitHub" (link).
- Release PR open → nothing per job; one line on the repo header ("Release #158 open · 14 commits · 6 jobs aboard").
The Foreman's `pr2`/`pr3` stages stay in the skill (they do the git work), but they are started from these nudges, and the nudges only exist when the finish line is before that stop. Past the line, nothing asks you anything unless you ask.

**D. The release train.** Staging and main stop being boxes: each repo gets one header line, "staging: 14 commits waiting · release #158 open · last release 2026-10-20", with the jobs aboard listed when you expand it.

What this gives: the daily loop ends at the finish line with a celebration; the long tail is a quiet list with one link per row; the map is rows you can read top to bottom; and a job's whole life is one track with one flag.

Not in this round: merging or approving from the dashboard (your rule: merges stay yours on GitHub).

## 11. Clarify: questions before the spec

The spec writer asks after drafting. The Kingdom "Audience" idea is to ask **before**, briefly, with consequences:
- A **Clarify card** at the start of an L2/L3 job (optional at L1, never at L0): the Foreman reads the request (and, when it knows the code, the paths it touches) and asks up to five questions, each with 2–3 options, a recommendation, and one line per option on what changes if you pick it ("Phoenix only: one office rule, ships this week · All offices: needs the scoping lens, L3"). Answered with keys `1`–`3`, or typed. "Use your recommendations" answers all at once (logged as decided on your behalf).

- Skill side: `feature/SKILL.md` Start gains the step; `status-json.md` gains `questions[].options[].consequence` and `stage: "clarify"`; `options.json` gains `clarify: "auto" | "always" | "off"` (default `auto` = ask when the request leaves a product decision open; the Foreman may send zero questions and go straight to the spec).
- Dashboard: the gate card renders consequences under options (one muted line each); Settings → Workflow has the default; the Desk shows it like any question.
