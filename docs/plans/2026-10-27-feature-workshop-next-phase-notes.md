## 1. What Feature Workshop is today (verified)

- A **local** Node dashboard on `127.0.0.1:4477` (new React view at `/next/`). It starts and drives one Claude Code **Foreman** per job through the Agent SDK (`dashboard/lib/driver.js`, `query()` with `canUseTool` and a `PreToolUse` hook). There is no `claude` command line; the SDK spawns Claude Code.
- The Foreman runs the `/feature` skill (the skill calls it the "conductor"). Stages: clarify → spec → wireframes → investigate → spec update → plan → build (one implementer per plan step) → tester → the human's manual test → review lenses (parallel subagents, each reads the diff itself) → PR #1 (fork → org, self-merged) → PR #2 (org → staging, Raj approves) → PR #3 (staging → main, release owner).
- **Levels** L0–L3 choose the stages. Risk floors (migrations, auth, scoping → L3; tables, office visibility, email, shared config → L2) live in both `lib/level-rules.js` and `job-options.md`. **Automatic level** is a dashboard setting, off by default; it re-checks the real diff after every build and only ever raises.
- **Job state** lives in `~/.claude/feature-work/<slug>/`: `status.json` (schema v1, documented in the skill, parsed leniently by `lib/status-json.js`, no strict validation), `workflow-status.md` (wins on conflict), `briefs/`, `options.json`, plan and test files, `review/`, `fable/`, `summaries/`, `wireframes.*`. The dashboard's own state is `~/.feature-workshop/` (`sessions.json`, `audit.jsonl`, `settings.json`, rules, notifications). **Decisions** is not a file: the Decisions tab is built from `audit.jsonl`.
- **Git:** the Foreman (skill) creates the worktree `../orbit-<slug>` from `moxie/main` and may create the org branch itself (create-only, standing yes). The dashboard never creates worktrees. Hard lines refuse any push to the org remote and force pushes; push, PR create/merge, `rm -rf` and db scripts always ask (or are covered in auto mode after the PR gate).
- **Try it:** `npm run dev` in the worktree, ports from **3001** in code (the prompt says 3011+; the code says 3001), `.env.local` copied from the main checkout with its URLs rewritten, local Postgres switch with an `__original` copy.
- **No ticket awareness:** no ORBIT key parsing anywhere in the dashboard; `status.json` has no ticket field. The skill's git workflow requires a real `ORBIT-n` before a branch exists and says links are registered on the ticket by a person "until the API/MCP exists".
- **Not present:** per-job lock files, a status.json schema validator, browser testing by the tester (it runs `npm run check` and `npm run build`; starting a server needs a yes each time), a program/packet mode (one coordinator over several jobs).
- **Mac/Unix-only pieces** (from the survey): Keychain read for usage meters (falls back to `~/.claude/.credentials.json`), terminal-notifier and osascript notifications (none at all off Mac), `open -a iTerm|VS Code`, Finder, Postgres paths, `ps`/`lsof` process listing (tries `/proc` first), `$SHELL -c` for Try it commands, process-group kill, `/tmp` hard-coded, hook file run by shebang. Skill side: `~` paths everywhere, `python3`, headless Chrome paths for Mac and Linux only, POSIX `install.sh`, Python `open()` without encoding, a `/briefs/` separator bug in `ship/preflight.py`. `nohup`, `kill` restarts and `~/Library/Logs` are not in the repo; they belong to how the dashboard is restarted by hand.
- Tests: `npm test` (about 385 node:test cases, server spawned with a fake query) and `web/` vitest (about 720). "No model calls in tests" holds by construction, not by a guard.

## 3. The vision in my words

Portal Feedback is where Moxie files and tracks Orbit bugs and feature requests. Feature Workshop becomes the way those tickets get built: a developer opens a ticket in the workshop, the Foreman runs the job with its gates, the ticket shows where the work is (branch, PRs, evidence, decisions), and the developer's own machine keeps doing the real work (worktrees, git, Claude, Try it, tests, the local database). The workshop grows from one person's local dashboard into something a small team uses: a hosted site (inbox, job screens, gates, roles, costs) with a local runner per developer that connects outward, accepts a fixed set of commands, and uses that developer's own Claude and GitHub logins. The coordinator-plus-packets way of working that built Portal Feedback itself (one Fable coordinator, parallel workers with owned files, one worktree, branch and port each, a decision register, gates before every merge, the human pushing) becomes a native shape of the workshop, so Vignesh stops juggling servers, worktrees and ports by hand. Playwright gives browser evidence per acceptance item. Each job's decisions and "not doing" list live where the team can see them. The whole thing runs on Windows, Mac and Linux, and the roadmap has stop lines so the company can say where to stop.
