# Feature Workshop redesign · design doc v0.2 (DRAFT, awaiting approval)

Built on the workflow-first plan with the best ideas from the other two grafted in; v0.2 answers the gap review. Inputs: the two research files in `docs/research/`, the current `dashboard/` code and the `/feature` skill. Line references checked on 2026-10-14. Nothing is built until section 14 is answered.

## 1. Vision

One window; the only thing asking for attention is a short **Needs you** list. Each job is a conversation with the Foreman where every decision arrives as a card you approve, edit or lighten in one keystroke. Small work (L0/L1) feels like a fast chat with a diff; big work (L3) like a guided review with a panel, and you move between them at any gate. Git, tests and the app preview sit beside the conversation, so "push to fork, open PR" is a palette command with a yes, not a stage. A usage ring says what the 5-hour window can still afford, a Haiku narrator (never Fable) says what the crew is doing, and every send shows whether continuing the Foreman or starting fresh is cheaper.

## 2. Information architecture

**Top bar (40px).** Job title + branch chip in the job's hue · stage stepper (skipped stages dashed; git is never planned ahead: a "Ship" segment appears only once a PR exists and lists what `gh` reports) · level chip · usage ring (5-hour %, weekly % on hover, reset countdown, "as of 14:02", dashed when older than 15 min) · Stats · ⌘K. Window title and favicon carry the Needs-you count.

**Jobs pane (240–280px, collapses to an icon rail).** Groups *Needs you / Running / Paused / Idle / Done*. `JobRow` = status glyph + label (never colour alone), stage chip, relative time, hue dot; paused rows say "resumes 3:42pm", parked rows say why. Done jobs keep their whole thread readable.

**Foreman pane (text ≤ 760px).** Your messages; `BriefCard` (collapsed to a headline once answered); `StageBlock` (collapsed "Build · 4m · 23 tools · +120/−8 · ≈ 2% of window", expanded = activity feed + handoff card); dim auto-allowed one-liners linking to the rule; gate cards pinned above the `Composer` (Send / Steer / Interrupt / Pause and the `ForemanChooser` line, section 5). A queued Steer message shows *queued → delivered → acted on* from the SDK stream; Pause keeps your unsent draft per job.

**Preview pane (40%, hideable).** Tabs **App / Diff / Tests / Terminal / Git**; "Open in" Chrome, iTerm, Terminal, VS Code, Finder.

**"How this job runs" drawer** (`JobSettingsDrawer`), the only per-job settings surface: level · three model dropdowns (Foreman / builder / checks) · reviewer chips · manual-test toggle · notes, saved to `<job>/notes.md` and read by every fresh Foreman. `NewJobSheet` takes description, repo, kind and optional past conversation or documents; the level is suggested after the first Foreman reply.

**⌘K** is an ARIA combobox listing only actions valid now. Keys: `a` approve · `⇧a` edit then approve · `r` revise · `o` other · `⌥a` approve after reset · `n` next gate · `j/k` jobs · `c` new job (⌘N belongs to Chrome) · `?` sheet; single-letter keys are ignored in text fields.

**Cut from today's UI** (`dashboard/public/`, all of it by phase 5): the per-repo board and pixel crew (`crew.js`, `pixelfont.js`, Crew-dex), the Fine-tune dialog, the six Details tabs, the Costs and History pages, the Confirm/Change/Later triplet, the permission tray and the sun/clock toggles; each has a home above or in Stats. **Kept backend** (`dashboard/lib/`): driver, policy, limits, local, history, options, close, features, session-log, cost, git, state, http-guard, repos, locate, stages, status-json, workflow-status, overview, markdown, permissions, compose, live (process list), hook-events + `dashboard/hooks/record.mjs` (the optional live link for terminal sessions with no log; it only links sessions to jobs, never supplies status). Extended as section 10 says; `markdown-tables.js` goes with the old UI.

## 3. Workflow levels L0–L3 and gate cards

Levels replace `flow`. `options.json` goes to `schema_version: 2`, **keeping** every v1 field and adding `level: 0|1|2|3` and `models: { foreman, build, checks }`. `lib/options.js` gains `LEVELS` and a `flowFor(level)` shim so an un-updated skill still reads a sensible `flow`, **pinning `models.foreman = Opus` for L3** because `FLOWS.large.model` is Fable today. `normalize()` maps v1 flows to levels; the dashboard warns when the installed `job-options.md` lacks the Levels table.

| Level | Runs | Review | Models |
|---|---|---|---|
| **L0 Tweak** | you describe → one build → `npm run check`/`build` → you look at the diff (a 5-line "what I'll change" card first is **Decision 8**, not a given) | none; diff shown | Opus Foreman; Sonnet build |
| **L1 Small** | quick plan (approve) → build → checks → you test → 1 lens | `feature-reviewer` | Opus |
| **L2 Standard** | short spec + plan (approve) → build in steps → tester → you test → 3–4 lenses | reviewer, permissions, tests, +db/ui if touched | Opus; Sonnet tester; Haiku conventions; optional Fable plan check |
| **L3 Large/risky** | spec → refine → investigate → plan (approve) → build in steps → tester → you test → full panel | all lenses + `feature-fable-check` | Opus Foreman; Fable at plan and review |

Inputs §2 defines L0 with no plan step; `job-options.md`'s "Never skippable" rule says every plan is approved first. That file is being edited anyway, so Decision 8 asks which. The L2/L3 spec yields a numbered acceptance checklist that test and review mark with evidence. Review↔fix loops stop at `review_rounds` (1–2 today in `lib/options.js`; phase 2 extends it to 1–3) and escalate to you.

**Suggesting a level, two sources on one card.** (1) `lib/levels.js`, no model: scans the description and, once a worktree exists, `git diff --stat` paths for migrations, auth/roles, `getScope`/`scopeWhere`, `entity_branches`, people/profile queries, email and shared config; a hit sets a floor (L2; migrations/auth/scope → L3). (2) The Foreman's first brief writes `suggested_level` + reason to `status.json`. `LevelCard` reads "Rules say L2 (touches migrations) · Foreman proposes L1 (contained to labels.ts)"; overrides are audited. Changing level later, from the chip, drawer or any gate card, writes `options.json` and shows the consequence inline ("L1→L2 adds: tester, permissions + tests lenses").

**Gate cards** (`GateCard.tsx`), one per decision, up to three questions combined, pinned above the composer. Buttons state their effect: **Approve** ("Approve plan v2 and start Build") · **Edit, then approve** (draft pre-filled; saving writes v(n+1)) · **Revise with feedback** · **Other guidance** · **Approve, start after reset**; **Stop job** behind ⋯ with the slug typed. Below: the "Also decided" list with one Override link, then chips for the **next step only**: *Skip next* · *Lighter* / *Heavier* · *Ask Fable* · *I'll do this part* · *L↑/L↓*, each patching `options.json` and appending one visible line through `composeReply`. Before build, test or review the card adds "Window: 61% used, resets 3:42pm · this stage typically ≈ 8% at L2".

**Permission cards and the trust loop.** `PermissionCard` carries risk tags from `policy.classify` reasons (*outside worktree*, *network*, *git push*, *migration*) and three actions: Allow once · Deny · **Always allow…**, which drafts the narrowest rule matching this call for you to confirm or edit; nothing is widened silently. `audit.jsonl` is the append-only log of every approval, denial and auto-allow; Stats mines it for rule suggestions (the "fewer permission prompts" backlog item).

**Safeguards.** A card stores the artifact version it was raised for; if that moves it greys out ("Plan changed since this was proposed", Reload). A gate untouched for 4 h notifies you and parks the job in *Idle*; nothing is ever auto-approved.

## 4. Git on the fly

Git actions are tools, not stages. The **Git tab** (`GitPanel`) shows live state from `lib/git.js` extended with `status()`, `aheadBehind()` (vs `origin` and `moxie/main`), `unpushed()` and `prs()` (`gh pr list --json`, in `GH_READ` already).

**Actions**, shown only when applicable, each through a `ConfirmSheet` printing the exact argv: *Commit* · *Sync with org main* (always `git fetch moxie main` first) · *Push to fork* (`origin` only; "org" never appears unless you type `push to org` in ⌘K, which opens a typed-slug confirm) · *Open PR* (base picker: org branch / `staging` / `main`; body from the template, `review.md` and check results) · *Request review* · *Merge* (number typed). `lib/git-actions.js` runs them with fixed `execFile` argv, no shell, every one audited; judgement calls (PR wording, conflicts) go to the Foreman as a message (Decision 3).

**Suggestions**, never required: git state (unpushed → "Push to fork?"; pushed, no PR → "Open PR to org branch?") and a `next_git` hint the Foreman may write to `status.json`, as one dim chip.

**Learned conventions.** `lib/conventions.js` watches `audit.jsonl`; the same two-step sequence twice for a repo triggers a one-time "Save as this repo's default" card. Observations live in `~/.feature-workshop/repos/<hash>/conventions.json`; "Save for the team" writes `<repo>/.feature-workshop/defaults.json` as a commit you push yourself (Decision 4). Conventions pre-select, never execute. A convention may also name **which merge ends the job**; until one is saved the dashboard asks once.

**Ready to merge** (bottom of the Git tab, also ⌘K) is **derived, not scripted**: local checks · review report · manual test · acceptance items · one row per PR that actually exists for the branch (`gh pr list --json number,baseRefName,reviewRequests,reviews,state`) with its CI (`gh pr checks`), unresolved threads (`gh api graphql`) and whoever `gh` says is requested · open Foreman questions · "another open job touches these files". No PR numbers, bases or approvers are hard-coded: one PR shows one row, a fork→org→staging chain three. The stepper's Ship segment is the same list. *Mark done* appears when the PR the convention names (or, with none, the one you pick) reports `MERGED`, and runs `close.js`'s checks.

## 5. Usage and cost on a shared plan

**Where the numbers come from (verified against `sdk.d.ts`).**
- *Window utilisation:* `rate_limit_event.rate_limit_info` (`utilization`, `rateLimitType`, `resetsAt`) reaches `driver.js:143` → `limits.js`. It arrives with the event stream, so v1 shows "as of hh:mm" and dashes the ring after 15 min. The SDK also has an on-demand `query.usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET()` returning `rate_limits.five_hour / seven_day` (`utilization`, `resets_at`); it is marked unstable, so v1 uses the stream by choice and adds a *Refresh* button that calls it behind a tolerant parser (a shape mismatch keeps the last stream value).
- *Foreman context size:* **not** `modelUsage[model].contextWindow` (`sdk.d.ts:1448`), which is the model's capacity beside `maxOutputTokens`. v1 sums each result message's `usage` (`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`), free with every reply, recorded by `driver.js`; `query.getContextUsage({ detail: 'summary' })` (`totalTokens`, `percentage`, `maxTokens`) is the cross-check when the chooser renders for a session idle past the cache. `costUSD` keeps the dollar side.
- New `lib/usage.js` appends all of it to `~/.feature-workshop/usage.jsonl` and feeds the ring. Budgets are **window percent first, API-equivalent dollars second**.

**Defaults.** Opus Foreman at every level. Investigate = Sonnet (Opus when risk triggers fire, as SKILL.md already does); build = Sonnet at L0, Opus otherwise; tester = Sonnet; conventions lens and narrator = Haiku; Fable only through `feature-fable-check` where the level names it.

**Concurrency.** Inputs §4.6 asks for a cap *across the team* with a queue and per-person usage. That needs shared state between machines, which v1 lacks, so v1 narrows to **2 active runs per machine** (`lib/scheduler.js`, extending `LimitWatch`'s queue; a third queues visibly); the team cap waits for the shared-folder question (Decisions 9 and 11).

**Continue, fresh or compact, per send.** `lib/foreman-policy.js` exports a pure `decide({ model, contextTokens, lastReplyAt, stageJustApproved, resetSince, now })` returning the options with estimates from the measured table:

| ~200k conversation | Opus | Fable |
|---|---|---|
| Reply while cached (idle < 1 h) | ≈ $0.04 | ≈ $0.05 |
| First reply after > 1 h idle (re-cache) | ≈ $1.60 | ≈ $4.00 |
| Fresh Foreman from job record + last handoff (~40k) | ≈ $0.32 | ≈ $0.80 |

Rule: **continue** while the last reply was < 55 min ago and context < 150k; **fresh** when (cold and > 60k) or > 150k or a stage was just approved or a reset passed since the last reply. Third option, **compact**: pausing a Foreman over 60k while its cache is warm offers to send `/compact` first, so the resume re-caches a summary, not the thread (the SDK reports it as `SDKCompactBoundaryMessage`; the trigger path is confirmed in phase 3). `ForemanChooser` shows radio chips, cheapest preselected: "Continue · re-loads 210k ≈ $1.60 ≈ 4% of window · Fresh from handoff ≈ $0.32". Fresh = `driver.start` with `sessionId: null` and the existing `/feature <slug>` bootstrap (`server.js:567`), which reads `workflow-status.md`, `options.json`, `<job>/notes.md`, the latest brief and the last handoff. Each generation (session id, reason, context size) goes to `<job>/foreman.json`.

**Caps and scheduling.** Per-job soft cap 25% of a window: warn at 80%, pause at 100% with "raise and resume". `⌥a` on any gate queues the approval in `scheduler.js` to fire at `resetsAt + 90 s`, staggered, defaulting to Fresh.

## 6. Visibility, and keeping reading small

Three layers, cheapest first, none written by the Foreman or Fable. Status comes from the SDK stream and process state, re-derived on restart, never from a hook-injected flag.

1. **Free event feed.** `lib/events.js` turns the SDK stream (subagent messages carry `parent_tool_use_id`) into typed events via `describeTool`, appends to `<job>/events.jsonl` and broadcasts; terminal-driven jobs keep the log tailer. `ActivityFeed` rows: "Builder · editing labels.ts", check exit codes, files touched, a timer, "quiet for 6 min" at 5 and 15 min.
2. **Haiku narrator.** `lib/narrator.js` runs its own `query()` (`model: haiku`, `maxTurns: 1`, `allowedTools: []`) on a capped ~4k-token excerpt; triggers: worker finished, check ended, a 2-minute tick **only while a worker runs**, debounced to one call per 60 s. Output: 1–2 plain lines + a progress guess to `<job>/activity.jsonl`. ≈ $0.0005 per update, per-job ceiling, pausable; it reads and never decides.
3. **Handoff cards.** Workers end by writing `<job>/handoffs/<nnn>-<stage>-<agent>.json` (done, remaining, commands + exit codes, issues, files touched); `worker-rules.md` gains the format, SKILL.md the rule "wake the worker once if the file is missing". `HandoffCard` ends each stage block; a fresh Foreman reads cards, not logs.

**Keep reading small** (inputs §4.7; `worker-rules.md` has none of it today). Phase 3 adds three rules there: `git diff --stat` first, full diff only for the files you need; long commands write output to `<job>/checks/<nnn>-<name>.log` and read back `tail -n 40` (plus `grep` for failures), never the whole file; briefs ≤ 200 words, handoff fields ≤ 5 lines. The dashboard matches: the Tests tab and `events.js` write every check's output to `<job>/checks/`, so workers tail the file the UI streams, and `HandoffCard` flags a brief over the cap.

## 7. Stats tab

Route `#/stats`, served by `lib/stats.js` (cached aggregate over session logs, `audit.jsonl`, `usage.jsonl`, `events.jsonl`, `activity.jsonl`, a new `stages.jsonl` from `status.json` transitions, and job records) at `GET /api/stats?range=&compare=`. Each chart has a one-line "what this tells you"; ranges and previous-period compare; CSV and Markdown export via `costCsv`/`costMarkdown`.

Sections follow inputs §8: **Overview** · **By model** (incl. cache hit ratio and re-cache cost) · **By job / level / stage / agent** (drill level → job → stage → session) · **Waiting on you** (top asking commands with "propose rule", the same draft as *Always allow…*) · **Waiting on agents** · **Top sinks** (cause tag + suggested fix) · **People** (own data in v1; optional import of a teammate's `stats-export.json`). Components `StatsPage`, `StatTile`, `BreakdownTable`, `DrillList`; Recharts in the token palette.

## 8. Preview, review and terminal

**App tab.** URL from `LocalRunner.portFor` (3001+). First use asks "Embedded or Chrome?" and stores `preview.default` per repo. Before embedding, `GET /api/preview/probe` `HEAD`s the local URL and checks `X-Frame-Options`, `frame-ancestors` and a sign-in redirect; if blocked, the tab says "This page can't be embedded (Google sign-in)" with *Open in Chrome* and remembers Chrome for that repo. **The dashboard's CSP must gain `frame-src http://127.0.0.1:* http://localhost:*`**; today's `default-src 'self'` blocks the iframe before any probe. Embedded view has a hue banner naming the job and device sizes. No proxy in v1.

**One dev server, one port, one DB (Decision 14).** The Chrome fallback solves only the iframe case. Google sign-in callbacks are registered for a fixed port, so a worktree on 3001+ may not sign in at all, and the DB switch is one shared resource. Three answers: (a) **mirror into the main checkout** (Conductor Spotlight style): "Test this job here" rsyncs the job's worktree into the main checkout, keeping the registered port and the DB switch, with a banner "main checkout mirrors job X", a clean-tree check and *Restore*; (b) **port-forward**: a tiny forwarder on the registered port pointed at the chosen job's 3001+ server, swapped per job; (c) **single-job testing** on the registered port. Whatever the choice, the **DB lock** is explicit: `local.js` records the holder in `~/.feature-workshop/db-lock.json`; a second job's "switch DB" or "start with DB" **warns and blocks**, naming the holder ("DB is held by *labels-fix* since 14:02 · release it there first"), never silently takes over. `close.js` gains a step before `removeWorktree`: `local.stopServer(slug)` and release the lock, so a worktree is never removed under a running server.

**Diff tab.** Scope switcher (this stage / last turn / whole branch) via `git.js` `commits`/`show` plus a new `diffRange(base, head)`; line comments batch into one "Send to Foreman" message. **`FindingsCard`** (phase 4): the reviewer report's items render as a stepper over the diff (`n`/`p`, each anchored to its hunk with severity and lens); each has *Send to fix* (collected into one fix message), *Dismiss with reason* (recorded in `review.md`) and *I'll do it*. Per-hunk keep/reject/revert and diffs grouped by logical change are deferred (section 13).

**Tests tab.** The local runner's presets (check / test / typecheck / lint / build / db status), output streamed and written to `<job>/checks/`, "rerun failed", the DB lock with its holder.

**Terminal tab.** xterm.js on the client, `node-pty` on the server (`lib/terminal.js`), one PTY per job in the worktree; output over the existing SSE, input by a small POST batched per frame: no `ws` dependency, no second auth path (Decision 2). "Open in" reuses `local.open`.

## 9. Design system

**Tokens and motion** are the research brief's §4 as written (oklch generator from base hue, accent hue and contrast; Inter 13px, Geist Mono tabular; 4px grid; transform/opacity only, nothing over 300 ms, nothing animating on j/k, palette or tab switch; reduced motion = fades), emitted by `web/src/theme/tokens.ts` → `tokens.css`. Dark first; light and high-contrast from the same generator.

**Fun touches (five, rare).** Per-job hue tinting dot, stepper and terminal cursor · Foreman glyph orbits while thinking, faster with more workers · one sub-1.2 s confetti burst when the job's **first PR opens**, whatever its base · "Claude's taking a breather, back at 3:42pm" with a countdown ring · a brief "naming…" shimmer while the branch is named.

**Accessibility.** Visible focus rings, combobox pattern for ⌘K, single-letter keys ignored in text fields, one debounced polite live region for streaming, every status with text. **Avoid:** the brief's list (glassmorphism, neon, colour-only status, toasts for decisions, role-play vocabulary, analytics sprawl, telemetry, any non-loopback listener).

## 10. Architecture and migration

**Front end.** `web/` (Vite + React 19 + TypeScript + Vitest): `src/app/` (shell, hash router), `src/panes/{Jobs,Foreman,Preview}/`, `src/components/` (every component named here), `src/views/{Stats,NewJobSheet,JobSettingsDrawer}`, `src/state/` (one `useWorkshopStore`, hydrated from `GET /api/snapshot`, patched by SSE), `src/theme/`. Served by `server.js` at `/next/` during migration; same CSP plus `frame-src`; no CDN.

**Transport.** SSE stays at `/api/events` with a typed envelope `{ v: 2, type, job, data, seq }` and new types `activity`, `narration`, `usage`, `git`, `scheduled`, `terminal`, `check`. Reconnect re-fetches the snapshot. Writes stay POST behind `http-guard.js`.

**Backend changes, all additive.** New: `lib/levels.js`, `foreman-policy.js`, `usage.js`, `events.js`, `narrator.js`, `handoffs.js`, `scheduler.js`, `git-actions.js`, `conventions.js`, `terminal.js`, `stats.js`, `preview.js`. Extended: `options.js` (v2 + shim), `git.js`, `driver.js` (result `usage` and `costUSD`, typed events, Steer delivery state), `limits.js` (scheduled queue, optional refresh), `local.js` (DB lock, `checks/` output), `close.js` (stop server, release lock), `state.js`. Routes: `/api/snapshot`, `/api/stats`, `/api/job/:slug/{level,activity,git/:action,schedule,terminal,handoffs,checks}`, `/api/preview/probe`, `/api/settings/preview`. Skill side, shipped with the code needing it: `job-options.md` (Levels, `models`, L0 wording per Decision 8), `worker-rules.md` (handoff file; `--stat` first; output-to-file + tail; brief and handoff caps), `SKILL.md` (wake-once, `suggested_level`, `next_git`, read `notes.md` at session start), `status-json.md`.

**Migrating while jobs run.** Front-end builds never restart the server, so UI phases ship any time. The SIGINT handler (`server.js:836`) stops every active run and persists only the limit queue, so **deploy backend changes between replies**; a restart banner lists cut runs and offers "Resend last message". v1 `options.json` files keep loading.

**Testability.** `foreman-policy`, `levels`, `events`, `stats` and `conventions` are pure with `node:test` tables; `demo/fake-query.js` is extended to emit `rate_limit_event`, result `usage`, `SDKCompactBoundaryMessage` and subagent messages so everything new runs in `npm run demo` without spending window; Vitest for components.

## 11. Phases

Each phase is a branch off main, one commit per step, pushed to the fork only, and ends at its gate.

1. **Shell and thread (M).** Vite app at `/next`: Jobs groups, thread with briefs and permission cards (*Always allow…* draft), Send/Steer (delivery state)/Interrupt/Pause (draft kept), snapshot + SSE replay, ⌘K, tokens, `NewJobSheet`; a whole job runs in the new UI under today's rules. **Gate: component list, token sheet, a screenshot of the shell.**
2. **Levels and gates (M).** `levels.js`, options v2 + shim + skill update, `LevelCard`, gate cards with chips, "Also decided", staleness guard, 4 h parking, drawer with `notes.md`; L0–L3 usable end to end. **Gate: level table, model defaults, the `job-options.md` diff including the L0 wording.**
3. **Visibility and usage (M).** `events.js`, narrator, handoff files, `checks/` output, the keep-reading-small rules in `worker-rules.md`, stage blocks, stepper, usage ring (+ experimental refresh), `foreman-policy` + `ForemanChooser` (continue / fresh / compact), per-machine cap, `⌥a` scheduling, fake-query extension. **Gate: after one real job, the narrator prompt and cadence, the thresholds and the skill edits.**
4. **Preview, review, git, terminal (L).** App (probe + fallback, CSP change, the Decision 14 mechanism, DB lock), Diff + `FindingsCard`, Tests, xterm + node-pty, git actions with confirm sheets, suggestions, conventions, derived Ready to merge, `close.js` server stop. **Gate: adding `node-pty`, the git command list, which actions the dashboard runs itself.**
5. **Stats and cut-over (M).** `#/stats`, `stages.jsonl`, exports; `/` points at the new app; `dashboard/public/` and its tests removed; README rewritten. **Gate: Stats on real data, then deleting `public/`.**
6. **Polish (S).** Fun touches, accessibility pass, `?` sheet, Moxie drift checks (`getScope`/`scopeWhere`, hardcoded office or branch names, gated feature without a seeding migration), team `defaults.json` export. **Gate: the touch list and the drift-check rules.**

## 12. Risks

- **Skill coupling.** Levels, handoff files, reading rules, `suggested_level` and `next_git` need the `/feature` skill changed in lockstep; the shim and a `schema_version` check keep old jobs loading, and the dashboard warns on a stale skill.
- **Backend restarts interrupt replies.** Deploy between replies; the "Resend last message" banner covers the rest.
- **The fixed port.** Sign-in on 3001+ is the real blocker, not the iframe; Decision 14 answers it. Mirroring overwrites the main checkout, hence the clean-tree check and *Restore*.
- **`node-pty`** is a native build; a failed build degrades to the command box.
- **SDK shapes move.** The usage refresh is explicitly experimental; keep parsers tolerant, with fixtures and the fake query in step.
- **Fresh Foreman loses chat nuance**; handoffs, `notes.md` and the decision log carry decisions, and Continue stays available for L3 refine interviews.
- **Narrator cost creep**; tick only while a worker runs, debounced, per-job ceiling.
- **Plan terms.** Several people on one Max seat may not fit Anthropic's terms; check before team rollout.
- **Scope creep.** v1 is this document; section 13 is the parking lot.

## 13. Deferred to v1.x

Named so they are chosen, not lost: **Services panel** (per-worktree port ranges, env, setup/run/teardown scripts) · **job presets** (level, skipped stages, reviewers, Fable checks, models) · a **"review later"** list separate from Needs you · **start a job from a GitHub issue, branch or PR** (v1's `NewJobSheet` offers past conversation or documents) · **element picker** · **generic drift warnings** (files outside the brief, same failure repeating; the Moxie-specific checks ship in phase 6) · **pane layout per job** · **Plan / Ask / Auto chip** per message · **per-hunk keep/reject/revert** and **diffs grouped by logical change** · **team concurrency cap and per-person usage** (with the shared folder) · **blocked-reason chips** with owner and action needed.

## 14. Decisions for you

1. **Default preview.** Embedded with probe-and-fallback, or Chrome always? *Recommend:* Chrome for the Orbit portal, embedded elsewhere; asked once **per repo** (deliberately, not once globally: the portal can't embed, other apps can).
2. **Terminal transport.** SSE + batched POST, or a WebSocket with `ws`? *Recommend:* SSE + POST; revisit if input latency is felt.
3. **Who runs mechanical git actions** (fetch, commit, push to fork): the dashboard or the Foreman? *Recommend:* dashboard, fixed argv, audited, typed confirm for push and merge.
4. **Where conventions live.** Per-machine only, or also a committed `<repo>/.feature-workshop/defaults.json`? *Recommend:* per-machine; the repo file only on an explicit "Save for the team".
5. **Continue/fresh thresholds** of 55 min / 60k / 150k, plus compact-on-pause above 60k? *Recommend:* yes, tunable, revisited after two weeks of Stats.
